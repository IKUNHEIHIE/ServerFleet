# ADR-TASK-001：批量任务调度与执行引擎

- 版本：v1.0（已批准版本；设计来源 v0.1 草案）
- 状态：**已批准（Accepted）；TASK-D1～D8 全部通过**
- 项目基线：Server Fleet v0.7
- 日期：2026-10-26
- 适用范围：主控 Go、Web React、Linux Agent、AI Tool、内置插件

## 1. 白话摘要

把主控想成调度室：用户或 AI 提出操作，调度室先确定有哪些服务器、什么权限、怎么分批，再把命令交给各 Agent；过程和结果可查询。所有任务都通过同一条通道，插件和 AI 不另外建立执行系统。**不引入 Redis、Kafka、独立任务微服务。**

## 2. 已确定架构约束（不得与既有 ADR 冲突）

1. 单 Go 主控，SQLite，Agent 主动建立 mTLS 连接。
2. Linux Agent 单二进制，默认 root 常驻；普通任务启动真正降权的子进程；root 任务经过主控授权与必要的一次人工确认。
3. AI 发起的任意 root Shell 必须由有权限的用户明确批准；AI/插件不自行批准或绕开任务引擎。
4. 插件使用统一的任务提交与状态接口；其前端页面由声明式配置生成。
5. 不存储或向命令进程暴露 Agent 私钥等不必要的敏感信息。

## 3. 正式批准决策（TASK-D1～D8）

| 编号 | 已批准选项 | 审核期间考虑的替代方案（未采用） |
|---|---|---|
| TASK-D1 执行方式 | 普通任务最多 5 台并行；批量 root/修改类任务先 1 台、再分批 5 台（人数不足时自动缩减）；管理员可修改上限 | 所有任务直接并发 |
| TASK-D2 失败处理 | 分批模式任一节点失败，则**不再启动后续批次**，已开始的节点继续收尾；普通并发模式失败节点不阻断其他节点 | 所有失败一律继续 |
| TASK-D3 离线节点 | 等待限定时间（默认 15 分钟），过期后标记未执行/已过期，不无限期追赶执行 | 离线立即失败 / 无期限等待 |
| TASK-D4 取消与超时 | 支持停止未下发的任务；对已运行任务尽力终止进程组并明确提示不能撤销已发生的变更 | 只支持取消未执行任务 |
| TASK-D5 断线与重试 | 执行 ID 在 Agent 本地持久化；结果不明的修改/root 命令**不自动重试**；仅安全可重试的查询等操作可按策略重试 | 所有失败自动重试 |
| TASK-D6 日志与审计 | 浏览器实时看各节点日志；主控持久化结果与审计，日志独立限额/按期清理 | 所有日志无限存数据库 |
| TASK-D7 资源架构 | Go 内置有界并发调度器 + SQLite（WAL）+ 既有 WebSocket Agent 通道 + Web SSE | 引入独立消息队列 |
| TASK-D8 操作入口 | Web、AI、插件共用 `jobs.submit`，执行前固化目标 Node ID、权限、命令及选项，权限在后端复核 | 各模块直接联系 Agent |

> **已批准的是默认行为和必须具备的能力**。批次大小、并发上限、离线等待时间等在许可范围内可配置，具体最大阈值以后用测试确定；不改变默认 1+5 / 5 并发 / 15 分钟过期的产品行为。

### 已批准默认调度行为的实施解释

- 普通任务最大同时执行 5 台，默认按 `parallel` 调度；root 及已知修改操作默认 `staged`，先试点 1 台、随后每批最多 5 台。后端已知道的结构化动作类型用于辨别修改性操作；无法可靠推断任意 Shell 的副作用，因此所有 root Shell 都进入分批默认策略，普通 Shell 仍依请求的明确策略与权限受限执行。
- 同批任意节点失败后只停止**后续批次**，不会无理由中断本批已开始执行的命令；手动 `resume` 仅对未执行批次有效。
- 离线等待的 15 分钟只针对**尚未启动**的节点任务；达到截止时间则 `expired` 且不再派发。已经运行的任务由执行超时和 `unknown` 状态管理。
- 任务审批继续绑定命令、目标、权限、执行参数及调度策略；修改任意关键值重新批准。

## 4. 用户流程

1. 在 Web 选择服务器或分组；**在提交时解析分组并固定实际 Node ID 列表**，避免执行期间分组变化导致误伤。
2. 填写命令或选择插件动作、权限模式、执行策略。
3. 主控鉴权，并对 root 人工任务一次性展示整个目标和命令请求确认；AI 发起的任意 root Shell 要求用户确认。
4. 任务被保存到 SQLite，按策略向在线 Agent 派发；任务在 Agent 上执行并报告状态和输出。
5. Web 显示各节点独立结果；分批任务发生失败时默认暂停未开始的批次，允许管理员查看原因后继续或终止。
6. 可查询历史任务与审计，日志按配额和保留期清理。

## 5. 任务状态（业务含义）

- **主任务（Job）**：待确认（如需要）、排队、运行中、已暂停、成功、部分失败、失败、已取消、已结束但结果待核实。
- **节点执行（Execution）**：排队、等待节点上线、已派发、已确认接收、运行中、成功、失败、取消中、已取消、超时、结果未知、过期未执行。
- 主控不能把“成功下发”当成“命令成功执行”。
- 任务被标记为取消，也不表示此前已执行的命令或变更被回滚。

## 6. 断线恢复与去重（不可省的安全底线）

- 每个 Job 有 `job_id`；每节点每次执行有稳定 `execution_id`，重发相同执行应沿用同一 ID。
- Agent 在启动子进程之前，**先持久记录**执行 ID、命令摘要、当前执行状态和关键时间，尽量保证同一执行 ID 不被再次启动。
- 若在“记录已运行”和“真正启动”之间崩溃，或者在执行完成但结果未上报时掉线，可能出现“结果未知”；这时不得声称执行成功，也不得盲目重跑有副作用的命令。
- 对不确定结果，管理员可检查现场后发起一个**新的、重新授权的执行**；这不能保证外部副作用恰好一次发生。
- 对只读查询，可通过显式策略有限重试；第一版不默认自动重试 root/修改任务。
- 离线过期的已批准命令不得在节点数天后重新上线时突然执行。

## 7. 取消、超时和节点安全

- 需要分别控制排队等待超时、节点等待窗口、实际运行超时。
- Agent 用受控子进程启动操作，设置执行身份（普通模式的 UID/GID 要实际降低，失败则拒绝执行）；设置工作目录、环境变量白名单、输出限额。
- 取消时先温和终止，再按超时策略强制停止进程组；部分 Shell 脱离进程组或已产生外部副作用，不能保证完全停止或回滚。
- 命令可能导致网络/SSH/Agent 自身重启；此类任务先单节点验证、谨慎批量推广。
- 普通任务和 root 任务不能同时对同一节点的相关资源不受控修改；第一版建议每节点最多一个修改类任务并发。只读任务可按配置并行。

## 8. 日志、结果与保留策略

- 任务元数据、审批及审计写入主控 SQLite；节点执行历史采用轻量本地持久记录。
- 实时输出从 Agent 通过现有 mTLS 通道传回主控，Web 通过 SSE 订阅。
- 日志写入限额、截断标识和轮转保留策略。**建议初始默认**每节点执行最多保留 5 MiB 输出、保留 7 天，均允许管理员调整。
- 输出中可能含密码与 Token：尽量避免秘密出现在命令参数中；采用权限限制、敏感字段打码和日志访问控制，但不得宣称可以识别全部泄露内容。
- SQLite WAL 适合第一版单主控，但需设置合理的写入批处理、忙等待、定期 checkpoint 和备份策略；不要把 SQLite WAL 文件放到网络文件系统作为跨机消息队列。

## 9. 接口草案（仅契约方向）

- `POST /api/v1/jobs`：创建任务；含 `target_node_ids`、`action`、`parameters`、`privilege: normal|root`、`strategy` 和幂等键。
- `POST /api/v1/jobs/{id}/approve`：完成明确授权的人工确认，沿用 v0.6 已定义的 `approve` 路径；权限、任务内容和目标快照均在服务端复核。
- `GET /api/v1/jobs/{id}`：查询总状态和节点摘要。
- `GET /api/v1/jobs/{id}/executions`：获取各节点详情。
- `GET /api/v1/jobs/{id}/events`：SSE 输出任务进度和日志；受访问权限与内容限额约束。
- `POST /api/v1/jobs/{id}/cancel`：取消待执行任务、请求停止已执行任务。
- `POST /api/v1/jobs/{id}/resume`：人工决定继续未执行批次，已执行节点不得默认重跑。
- Agent 协议：`TaskOffer / TaskAck / TaskStarted / TaskOutput / TaskFinished / TaskCancel / TaskStateSync`；均包含 `job_id`、`execution_id`、`node_id`、序号、版本等必要字段。
- 后端任务执行认证和审计走现有 `ADR-PRIV-001`；**不增加独立特权 Helper 或签名票据**。

## 10. 验收测试

1. 选择 50 台服务器，用户可看到所有节点分别成功、失败、执行中或等待中的状态。
2. root/修改任务采用单节点测试与分批策略，首批失败不启动后续批次。
3. 在运行中关闭浏览器、重启主控，已记录任务与执行状态能恢复；无法确认的结果显示“未知”。
4. Agent 断线后重新连接，不会因为重复下发同一个执行 ID 自动二次执行已开始的 root 命令。
5. Agent 离线超过期限后重新上线，不执行已过期命令。
6. 取消任务不把已执行变更标记为“已回滚”。
7. 普通任务子进程身份实际非 root；root 操作经过一次明确授权。
8. 插件与 AI 无法绕过统一授权、审计和既定的批量执行机制。
9. 日志超过限额被截断且明确提示，不导致内存无限增长。
10. 1c1g 主控管理几十台节点时，以实际压测验证连接、内存、CPU、SQLite 和日志吞吐。

## 11. 明确不纳入第一版

- Kubernetes、Redis、Kafka、独立调度微服务。
- 大型工作流编辑器、跨任务复杂依赖图、自动回滚任意 Shell 操作。
- 对每条 Shell 命令做可靠的“高危黑名单识别”（无法保证完整识别）。
- 对有副作用操作声称“恰好执行一次”。
- 通过浏览器关闭来隐式取消全部后台任务。

## 12. 与已批准 ADR 的关系

- `ADR-BOOT-001`：任务通道复用 Agent mTLS 身份和安全注册。
- `ADR-PRIV-001`：普通/root 执行、人工确认、AI 无法自行批准高权任务、SQLite 审计。
- `ADR-PLUGIN-001`：插件基于统一 `jobs.submit` 能力提交任务，声明式 UI 负责配置和展示。
- `ADR-WC-001`：证书部署与续期也应提交到同一任务引擎，但证书私钥本地保管规则不变。

## 13. 批准记录与决策边界

- **批准人**：项目发起人；**批准日期**：2026-10-26；**批准内容**：TASK-D1～D8 全部采纳。
- **写入版本**：Server Fleet 文档 v0.7，PRD、架构方案和 API 契约均已同步。
- **接口一致性**：历史任务审批路径已是 `/approve`，本次 ADR 使用同一路径，不额外建立并存的 `/confirm`；新增 `/resume` 只作用于暂停、未开始的批次。
- **安全先决**：继续服从 ADR-PRIV-001 的 root 人工确认与 Agent 去重，服从 ADR-BOOT-001 的 mTLS 注册、ADR-PLUGIN-001 的统一任务入口和 ADR-WC-001 的网站 TLS 私钥隔离。
- **后续可变**：确切 OpenAPI 字段布局、性能阈值、日志建议数值、流控实现细节未在本次冻结；不得以它们未定为由放宽已批准的审批、幂等和失效语义。
