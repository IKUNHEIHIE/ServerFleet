# Server Fleet v0.9 — 正式开发前文档审查报告

**审查日期：**2026-10-29  
**审查性质：**只读审查，不改变已批准需求或 ADR  
**产品基线：**`ServerFleet-Functional-Requirements-v0.9.md` + `Plugin/xray-manager/FR-PLUGIN-XRAY-001.md`  
**接口基线：**`ServerFleet-API-Contract-v0.9.yaml` + `Plugin/xray-manager/Xray-Manager-OpenAPI.yaml`  
**历史架构依据：** Server Fleet v1.1 架构方案与已批准的 ADR-PLUGIN-001、ADR-DEPLOY-001、ADR-AI-001、ADR-TASK-001、ADR-PKI-OPS-001 等。

## 1. 结论

**产品方向已相对完整，尚未达到可以把整份 v0.9 OpenAPI 直接交给多个开发 Agent 并行实现的程度。** 建议先进行一次 **docs-r2 文档勘误 + 产品实现边界冻结**，再评审架构 ADR 冲突，最后冻结代码级接口并开启 M0/M1。全部已批准功能应保留；开发优先级不等同于删除需求。

- 产品功能：大模块均有明确定位；对用户工作流、权限与异常状态已有相当描述。
- 文档状态：存在旧版本状态残留、重复章节号、交付物引用错误。
- OpenAPI：主契约 119 Paths、151 Operations、132 Schemas；Xray 独立契约 19 Paths、23 Operations、30 Schemas。JSON/YAML 解析与引用检查并不等同于完整的规范及行为验证。
- 已检查所有 API 路径参数，经共享 `$ref` 参数解析，**未发现未声明的必需路径变量**；不能把只按内联参数检查产生的假阳性当成缺陷。
- 架构决策：至少三处新需求实质改变旧 ADR 的已批准范围，必须显式修订。
- 软件状态：当前 HTML 是演示原型；真实 Controller/Agent、权限、PKI、Xray 安装与统计尚未实现。

## 3. 必须先处理的产品/安全决策冲突（建议 P0）

### ADR-PLUGIN-001 与 v0.9 插件机制

已批准旧 ADR `PLUGIN-D2`：第一版后端 **编译期内置**，仅 UI schema 动态读取；独立进程/外部后端留给后续版本。后续明确批准的新需求：**首版 Xray 插件不预编译进核心 Release、GitHub Plugin/ 目录按需下载、热安装/停用/更新、声明式及受控 WASM 运行**。两者不能同时作为当前有效实现方案。建议提交 `ADR-PLUGIN-001 v0.3`：保留声明式 UI/统一能力/禁止脚本注入原则，明确新版可选插件的运行与权限模型，旧 D2 标记为已被新决策替代（Superseded）。

### ADR-DEPLOY-001 与网关新建向导

旧 `DEPLOY-D2`：首版识别和接管**已安装** Nginx，不负责为新节点自动安装。后续获批的「新建网关」要求从在线节点选择并自动安装 Nginx，通过配置/服务/健康检查才获得调度资格。建议修订范围：保留接管已有安装的非破坏性路径，增加**明确许可下的受控首次安装**路径；两个流程都不得覆盖非受管 Nginx 配置。

### ADR-AI-001 / ADR-PRIV-001 与三级审批

旧 `AI-D5`、`ADR-PRIV`：AI 发起的任意 root Shell 必须管理员 Web 真正批准。v0.6 起的“完全访问”允许限时免逐项审批。建议冻结规则：**完全访问仅免除允许自动审批的部分合法操作的逐项确认；不得豁免被硬性保护的任意 root Shell、私钥/凭据导出、修改会话授权、主控信任变更等动作**。资源范围与用户原始 RBAC 也绝不自动扩大。正式 ADR/接口测试须覆盖。

### 灾难恢复已具有批准的具体决策

旧 `ADR-PKI-OPS-001` 已批准：每日加密备份、7 日 + 4 周保留、SFTP 异地、离线恢复私钥、CLI 一次性恢复、隔离恢复模式、季度演练。现行 v0.9 功能描述偏概括，不应在技术讨论时重新把这些已批准值当成完全未定；若需要改变，提出增量修订而不是忽略旧 ADR。

## 4. OpenAPI 和跨层契约缺口

**现有数量不是接口完整性的证明。** 主契约大量覆盖业务展示/异步任务，但真实开发最初必需的基础功能尚未形成可直接生成代码的完整契约：

1. **认证与会话、用户与角色、审计查询**：当前无 `/auth/*`、`/users/*`、`/roles/*`、`/audit/*` 等可供用户登录/权限配置/审计页面闭环的规范路径；必须明确最小授权模型与拒绝结果。
2. **节点完整生命周期**：虽有 `/nodes` 列表、注册令牌、审批，但节点详情、修改、禁用/删除、Agent 状态/能力查询、身份轮换/吊销、连接诊断结果的接口需补齐或明确由何种资源提供。
3. **任务事件与生命周期**：已有 `/tasks` 创建、详情、安全执行接口，但任务列表/取消/恢复/逐节点执行日志与 SSE 流的统一 API 未完整可见；不能只依据旧 ADR `/jobs` 路径直接开发，须确定 `/tasks` 与 `/jobs` 的唯一命名。
4. **证书与备份生命周期**：已有内部证书批量下发和恢复校验接口，但公网证书申请/列表/续签、备份列表/创建/下载/保留等用户可见行为尚未在主契约里完整覆盖。
5. **AI 对话与消息**：已有会话创建/授权/审批/执行工具端点，但消息发送、流式 token / 工具事件消费、会话历史管理与错误恢复的真实协议需定义。
6. **Agent 通信契约**：目前是管理 HTTP OpenAPI，不能代替 Agent 的 Protobuf/mTLS 注册与任务消息契约。必须另列消息契约、版本协商和错误/重试规则。
7. **插件的扩展 API**：只有具体 Xray 路由，不等于已经定义通用的插件声明 UI 获取、受控动作/数据源注册、插件版本兼容与能力表。
8. **错误与分页统一**：部分查询接口仅列成功响应；需要全局 `ErrorResponse`、访问拒绝、版本冲突、幂等冲突、资源失联、分页/过滤标准，尤其是 `409` 与 `412` 的分工。
9. **跨模块授权**：服务发布间接操作网关、DNS Zone、证书与后端，AI 仅授权节点/服务组时能否触发 DNS/证书操作必须有具体硬规则，不能依赖目标 Node ID 来隐式扩权。
10. **接口验收**：对每个正式 API 建立请求/响应样例、负面测试、并发与失败重试契约。先锁定关键基础接口，再扩展到全部 151 操作。

**检查结果说明：**本次解析并验证了主/插件契约的路径、操作 ID、共享引用及路径参数。主/插件 Xray 同名操作和 schema 内容未见差异。但仍需规范级 lint、API 示例测试与真实实现联调。

## 5. 功能需求中需要再明确的最小产品规则

| 议题 | 需明确的用户可见规则 | 默认建议 |
|---|---|---|
| 产品的第一版范围 | 已批准功能过多，开发者无法判断 M0、M1 哪些必须可用 | **功能总清单全保留；M1 只冻结最小闭环；余项列 M2/M3** |
| 独立用户/组织 | 单管理员、多个管理员与跨组织权限是否同时首发 | 第一版单组织，管理员/运维/只读三角色；无多租户 SaaS |
| 监控与告警 | 资源监控、网关检测、外部可用性状态优先级 | 区分 `node_online`、`service_healthy`、`gateway_eligible`、`probe_unknown`，禁止互相代替 |
| 删除/卸载语义 | 删除分组/服务组/插件/受管实例如何影响依赖 | 先列影响，再二次确认；插件卸载不动节点软件 |
| 任务与操作确认 | 「完全访问」是否免除高风险管理员确认 | 明确不能免除硬性管理员确认，且所有工具仍执行资源权限交集 |
| 节点可控权限 | Agent 常驻 root，哪些高风险动作可授权插件执行 | 每种动作用最小权限白名单，禁止任意系统命令隐式升级 |
| Xray 实例接管 | 已存在实例但不符合标准目录/服务管理方式 | 默认仅只读检测，接管必须单独批准并保留可恢复备份 |
| 资源轻量化 | 一套系统有大量功能但目标是小 VPS | 确定核心/Agent 空载 RAM、CPU、网络采样、持久数据增长目标，后续真实测试验证 |
| 数据保留/体积 | 审计、任务日志、流量采样和 AI 会话增长 | 各类数据设置默认保留、大小上限、清理策略、可见告警；暂不给未经实测数字承诺 |

## 6. 建议的开发准入门槛（不是技术栈方案）

**G0 产品范围冻结：** 
- 批准的需求全部保留，但标明 M1 最小可运行闭环（注册+鉴权+节点状态+基础监控+有审批的任务+审计+基础备份）。
- 各业务功能分成「核心首次可用」「第一版完整版」「后续增强」，不要让“v0.9 文档有此功能”变成“M0 全部开发”。
- 每项功能有正常/失败/越权场景、验收方法和依赖功能。

**G1 架构决策对齐：** 
- 修订 ADR-PLUGIN、ADR-DEPLOY，明确 ADR-AI 与完整访问的不可越过的硬限制，保留 PKI/TASK/BOOT 已批安全底线。
- 确定模块所有权、插件运行边界、mTLS/Protobuf、任务持久化、凭据隔离和备份恢复与既有 ADR 的关系。

**G2 技术契约冻结：** 
- 建立 Controller 管理 OpenAPI + Agent Protobuf + 插件声明/权限 Schema 三份接口契约。
- 用契约 lint、示例请求/响应、负向安全测试证明一致性，再生成客户端或让多个 Agent 并行开发。

**G3 开发实施：** 
- 先完成 M0 Monorepo/CI/基本 UI + M1 安全最小闭环；通过真实节点 e2e 测试后再扩展网关、DNS、证书、服务组、AI、Xray 插件等功能。
- 使用 Git worktree / 多 Agent 时，统一以 G0～G2 冻结的规范为源，不允许某一个开发 Agent 独立推翻安全或接口契约。
