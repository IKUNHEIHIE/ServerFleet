# ADR-WC-001 — 公网证书的签发、私钥归属与跨节点部署策略

> 项目：轻量级 AI 服务器群控平台  
> 版本：v0.3 · **Accepted（已批准）** · 2026-10-26  
> 日期：2026-10-26  
> 关联：[PRD v0.2](./01-PRD-需求文档-v0.5.md) · [架构方案 v0.2](./02-技术架构方案-v0.5.md) · [API v0.2](./03-API与通信协议-v0.5.md)

## 1. 已确认前提（本 ADR 不重议）

- 主控原生集成 Cloudflare API 和 ACME；Cloudflare 主要提供受管 DNS 和 DNS-01，方便配置网站/API HTTPS 和通配符证书。
- 私有 Root CA 离线，Intermediate CA 在线；该体系只负责主控—Agent 私有身份，不能替代公用 CA。
- Agent 通过 mTLS 主动直连主控，所有证书操作通过主控任务引擎审计；Cloudflare Token 和 ACME 账户私钥不能下发到 Agent。
- 主控应统一管理公开证书生命周期、关联的域名和节点、任务计划与到期状态。

## 2. 先区分三个决策维度

1. **谁发起/协调 ACME 订单**：建议始终由主控统一协调 DNS-01 和 ACME 验证，以免分发 Cloudflare API Token。
2. **谁生成/持有网站 TLS 私钥**：主控集中保管；节点本地保管；或者由受限 TLS 网关保管。这一维度是本 ADR 的核心。
3. **证书覆盖哪些域名**：单个主机名（`api.example.com`）；受限子域的通配符（`*.apps.example.com`）；整域通配符（`*.example.com`）。覆盖面独立于私钥保管位置，是另一个风险维度。

ACME *账户密钥*、Cloudflare *API Token*、私有 *CA 签发密钥* 与网站 *TLS 私钥* 是四种完全不同的秘密，不能在设计文档或程序变量中混淆。

## 3. 四种候选架构

| 方案 | ACME/DNS-01 | TLS 私钥归属 | 优点 | 主要缺点 | 评估 |
|---|---|---|---|---|---|
| A. 集中共享通配符 | 主控 | 主控生成，再复制到多台 VPS | 一张证书管理简单，新增节点部署较快 | 一个节点泄露密钥，整张共享证书必须应急轮换；复制链路与落地副本增大暴露面 | **不推荐默认采用** |
| B. 各节点独立通配符 | 主控协调签发（不是 Agent 自行持 DNS Token） | 每个 Agent 本地独立生成一把密钥 | 任一私钥泄露不会直接泄露其他节点私钥；可独立吊销 | **仍能冒充其通配符覆盖的其他子域名**；同一 SAN 多节点重复签发还会碰到 ACME 额度限制 | 有条件支持 |
| C. 主控统一协调、节点独立主机名证书 | 主控 | 每个 Agent 本地生成独立私钥与 CSR | 最小域名权限；泄露影响较小；集中 DNS/证书管理仍保留 | 首次实现需开发 CSR/订单/安装/服务重载工作流；证书数量稍多 | **推荐默认策略** |
| D. 集中 TLS 入口网关 | 主控 | 只有某个专用入口节点/网关持有通配符私钥 | 不向普通应用 VPS 分发通配符密钥；集中 HTTPS 接入 | 增加流量转发、延迟、可用性与扩容成本；不是轻量 VPS 群控默认形态 | 特定业务可选 |

**重要区分：**即使使用方案 C，主控仍然统一管理 ACME/Cloudflare/DNS 和证书任务；“节点保管私钥”不等于“每台节点必须自己申请证书”。

## 4. 为什么“每节点不同的通配符私钥”仍有横向风险？

例如 Tokyo-VPS 持有独立密钥、证书 SAN 是 `*.example.com`；US-VPS 也持有另一把独立密钥、SAN 同样是 `*.example.com`。Tokyo-VPS 被入侵后，攻击者虽然没有拿到 US-VPS 的密钥，却能用 Tokyo-VPS 的有效证书和密钥，在网络欺骗、DNS 篡改或代理配置错误等条件下冒充 `api.example.com` 等同一通配符范围内的站点。

证书身份覆盖面是 `*.example.com`，不会因为不同服务器持有不同私钥而自动细分。因此**独立密钥解决“单把密钥到处复制”的问题，却不自动缩小证书可冒充的域名集合**。

`*.example.com` 既不覆盖根域名 `example.com`，也不覆盖 `foo.bar.example.com`。需要时可以为特定子域使用 `*.apps.example.com`，把不同业务域名隔离为更小的授权域。

## 5. 推荐策略（仅为审核提案）

### 5.1 默认路径：每节点独立的精确主机名证书

用户给 US-VPS 的网站绑定 `api.example.com`：

1. Web 提交受控证书/域名部署计划；主控验证管理员对 Zone、主机名和节点的权限。
2. Agent **本地生成 TLS 私钥**（单独于 Agent mTLS 身份密钥），返回对应 CSR 和 CSR 校验信息。私钥不通过任务日志或任何普通文件接口回传。
3. 主控使用自己管理的 ACME 账户发起订单，通过 Cloudflare API 写入必要的 `_acme-challenge` TXT 记录并等待权威 DNS 可查询。
4. 主控把 Agent 的 CSR 交给公开 CA 完成签发，收到公开证书链；**主控只返回证书链，不返回私钥**。
5. Agent 将新证书和本地密钥原子安装到仅授权账户可读取的路径；在校验证书链/SAN/私钥匹配后按受控适配器热重载 Caddy、Nginx 等服务。
6. 主控检查源站 HTTPS 实际握手/证书、记录部署状态；未成功则尽可能回滚到上一套证书和配置。
7. 续期由主控统一排程，支持 ACME ARI、幂等请求、限流和错峰；Agent 续期时可轮换本地 TLS 密钥。

### 5.2 通配符作为高级选项，而非全域默认部署证书

- 有动态子域需求时允许签发 `*.apps.example.com` 等限定业务范围的通配符。
- 推荐通配符仅部署在**一台专用入口网关**或**同一安全边界、确有需要的节点**；跨多个信任域部署需二次确认。
- 对多节点分别签发同一 SAN 通配符时，必须做申请节流、同一域名证书数监控、续期编排和故障处理。**每节点证书虽然私钥不同，但授权范围仍同样广。**
- 首版可以保留“通配符证书申请”和“单节点部署”能力；跨节点**共享同一私钥**建议作为 P2 高风险可选功能，并保持默认禁用。

### 5.3 如果用户坚持方案 A（集中共享）

至少需要：明确列出所有目标节点和身份；二次审批；密钥在主控中由独立密钥管理模块保护；仅经 mTLS 与授权任务下发；目标 Agent 使用 0600 等受限权限保存；日志/备份/诊断严禁暴露；节点卸载和失陷触发整张证书重新签发、所有已部署节点同步更换；明确无法仅回收已复制的密钥副本。此路径仍应标为高风险。

## 6. Cloudflare DNS Token 风险（与证书保管独立）

即使主控不存储任何网站 TLS 私钥，主控如果遭入侵且攻击者获得能够修改 `_acme-challenge` 的 Cloudflare Token，仍可能未经授权为相关域名签发新证书。因此：

- Cloudflare Token 不分发 Agent，限定最小 Zone 范围和权限；应用层再限制其可变更的记录，并审计所有 DNS-01 操作。
- 更高安全级别可将 `_acme-challenge` 通过 CNAME/NS 委派到单独的验证子域/Zone，再仅给主控该验证 Zone 的 API Token，以缩小可修改记录的范围；此功能可 P2。
- 禁止普通 AI Tool、第三方插件读取/导出 Cloudflare Token 或 ACME 账户密钥。

## 7. 资源与复杂度考量

| 维度 | A 集中共享 | B 节点独立通配符 | C 节点独立主机名 | D 网关 TLS |
|---|---|---|---|---|
| 节点常驻新增进程 | 无 | 无 | 无 | 需网关服务 |
| 主控签发订单数 | 较少 | 随节点数增长 | 随独立主机名增长 | 较少 |
| Agent 专属扩展 | 文件安装 | CSR + 安装 | CSR + 安装 | 网关集成 |
| 证书泄露影响范围 | 整个共享 SAN 与部署集合 | 单把密钥，但可冒充整个通配符 SAN | 对应 SAN 内的主机名 | 对应网关证书 SAN |
| 更换证书时受影响目标 | 所有共享节点 | 对应节点 | 对应服务/节点 | 入口网关 |

B 与 C 的 Agent 能力几乎一样：均为“本地生成 TLS 私钥和 CSR + 接收证书链 + 原子部署”。因此即使用户决定支持 B，实现 C 也基本不会额外显著增加常驻 Agent 复杂度。

ACME 速率限制会变化，需以实时官方文档为准。大规模重复创建具有相同 SAN 的证书不等于无限免费签发；应使用 ACME Staging 做开发、应用端按证书 ID 做去重，续期支持 ARI 并进行告警。

## 8. API/任务/数据结构建议（不冻结）

- `CertificatePolicy`: `dns_names`, `issuer`, `key_custody`, `deployment_scope`, `renewal_policy`, `risk_level`。
- `CertificateOrder`: `order_id`, `zone_id`, `csr_ref`, `acme_account_ref`, `dns_challenge_status`, `certificate_id`, `expires_at`。
- `CertificateDeployment`: `certificate_id`, `node_id`, `service_adapter`, `target_path_ref`, `public_key_fingerprint`, `status`, `last_checked_at`。
- 预期任务动作：`tls.generate_csr`、`tls.install_certificate_chain`、`tls.validate_endpoint`、`tls.reload_service`。共享私钥导入若支持，应另有高危的 `tls.import_shared_key`，不复用通用任务动作。
- `key_custody` 拟支持 `node_local`、`gateway_local`；`master_shared` 仅在明确审批支持后加入。
- 证书部署权限至少包含 `domains:read`, `certificates:issue`, `certificates:deploy`, `nodes:manage_service`，高危共享密钥另设权限。

## 9. 验收测试建议

1. 目标 Agent 生成 CSR 后，主控抓取数据库/日志/任务明文不能获得 Agent 私钥。
2. 主控 Cloudflare Token 无法从节点、AI 对话和插件 API 读取。
3. `api.example.com` 证书部署到 US-VPS 后，Tokyo-VPS 不会自动收到相关私钥/证书部署任务。
4. `*.example.com` 的共享私钥部署若未来开放，未明确审批不能执行。
5. CSR 的 SAN 与用户获授权域名不一致时拒绝签发；目标节点不在授权范围时拒绝任务。
6. 更新失败不会留下证书/私钥不匹配导致 HTTPS 长期不可用；能回滚并发出可操作告警。
7. 模拟 ACME DNS-01 失败、Cloudflare 429、CA 429/Retry-After、节点离线与主控重启，证书任务可恢复且不会造成重复签发风暴。
8. 节点证书吊销与公共网站证书撤销路径各自独立，不混淆 Agent mTLS 身份与网站 TLS 证书。

## 10. 最终决策与批准状态

**正式决策（项目所有者已批准）**：采用 C 为默认：主控统一 Cloudflare + ACME + 生命周期；每个 Agent 本地生成和持有网站 TLS 私钥，默认申请绑定具体主机名的独立证书。允许签发通配符，但跨节点共享同一张通配符证书与私钥不作为默认能力，首版只支持指定节点/单入口部署；同 SAN 但不同私钥的“每节点通配符”作为按需高级配置。若确实需要跨节点共享同一私钥，需另经审批设计高风险路径。

**状态：Accepted（已批准）**。项目所有者已于 2026-10-26 明确认可本 ADR 的五项规则。核心约束为：

1. 主控统一管理 Cloudflare、ACME、证书生命周期和部署任务。
2. 每台被控 Agent 本地生成、保管网站 TLS 私钥；私钥不得上传主控。
3. 默认按具体主机名签发独立证书，限制 SAN 授权范围。
4. 通配符按需申请，优先限定子域名范围，部署到指定单节点或专用网关；同 SAN 不同私钥仍有跨子域冒充风险。
5. 首版禁止跨多节点共享同一通配符私钥；未来如需开放，另起 P2 安全 ADR 评审。

上述为**已批准的产品与安全规则**，不等于所有 API 字段/代码实现已经冻结。若要改变该决策，须创建新 ADR 或正式修订本 ADR，并说明安全影响。
